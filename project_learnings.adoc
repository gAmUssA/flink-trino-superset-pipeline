== 📋 Project Overview

This document summarizes the key learnings and issues addressed in the Flink-Trino-Superset data pipeline project.

The pipeline consists of the following components:

* *Data Generator*: Python application that produces synthetic user activity and sensor data
* *Apache Kafka*: Message broker for data ingestion (running in KRaft mode without Zookeeper)
* *Apache Flink*: Stream processing framework for real-time data processing
* *Apache Iceberg*: Table format for data lake storage
* *Trino*: Distributed SQL query engine
* *Apache Superset*: Data visualization and dashboarding

== 🔄 Data Flow

1. The *Data Generator* produces two types of sample data:
   * User activity data (page views, clicks, searches, purchases, etc.)
   * Sensor data (temperature, humidity, pressure, light, motion)

2. Data is sent to *Kafka* topics:
   * `user-activity` topic for user events
   * `sensor-data` topic for sensor readings

3. *Flink* jobs consume data from Kafka:
   * `UserActivityProcessor` processes user activity events
   * `SensorDataProcessor` processes sensor data

4. Processed data is written to *Iceberg* tables:
   * `iceberg.warehouse.user_activity`
   * `iceberg.warehouse.sensor_data`

5. *Trino* provides SQL querying capabilities over the Iceberg tables
   * Pre-defined views for analytics: `hourly_user_activity` and `sensor_stats`

6. *Superset* connects to Trino for data visualization and dashboarding

== 🔍 Key Components Analysis

=== Data Generator

The data generator is a Python application that:

* Uses the Faker library to generate realistic data
* Produces two types of events: user activity and sensor data
* Sends data to Kafka topics with configurable rates
* Simulates real-world patterns with randomized data
* Supports both local and cloud (Confluent Cloud) Kafka environments

The data generator is configurable via property files located in the `config/` directory:

* `config/local/` - Configuration for local Kafka development
  * `kafka.properties` - Local Kafka connection settings
  * `topics.properties` - Kafka topic names for local environment
* `config/cloud/` - Configuration for Confluent Cloud
  * `kafka.properties` - Confluent Cloud Kafka connection settings
  * `topics.properties` - Kafka topic names for cloud environment

The environment can be switched by setting the `KAFKA_ENV` environment variable to either `local` or `cloud`.

=== Flink Jobs

The project uses Flink SQL for data processing, following the recommended approach of using Flink Table API or SQL instead of the DataStream API. Two main SQL jobs process data from Kafka:

==== user-activity-to-iceberg.sql

* Defines a Kafka source table that reads from the `user-activity` topic
* Creates an Iceberg sink table for storing processed user activity data
* Transforms and inserts data from Kafka to Iceberg
* Includes watermark definitions for event time processing
* Handles JSON parsing with error tolerance

==== sensor-data-to-iceberg.sql

* Defines a Kafka source table that reads from the `sensor-data` topic
* Creates an Iceberg sink table for storing processed sensor data
* Transforms and inserts data from Kafka to Iceberg
* Includes watermark definitions for event time processing
* Handles nested JSON structures (e.g., location data with lat/lon/facility)

=== Iceberg Tables

Two main tables are defined in the Iceberg catalog:

==== user_activity

[source,sql]
----
CREATE TABLE IF NOT EXISTS iceberg.warehouse.user_activity (
    user_id VARCHAR,
    event_type VARCHAR,
    event_time TIMESTAMP,
    session_id VARCHAR,
    ip_address VARCHAR,
    user_agent VARCHAR,
    page_url VARCHAR,
    total_amount DOUBLE
)
WITH (
    format = 'PARQUET',
    partitioning = ARRAY['day(event_time)']
);
----

==== sensor_data

[source,sql]
----
CREATE TABLE IF NOT EXISTS iceberg.warehouse.sensor_data (
    sensor_id VARCHAR,
    sensor_type VARCHAR,
    event_time TIMESTAMP,
    latitude DOUBLE,
    longitude DOUBLE,
    facility VARCHAR,
    sensor_value DOUBLE
)
WITH (
    format = 'PARQUET',
    partitioning = ARRAY['day(event_time)', 'sensor_type']
);
----

=== Analytics Views

Two pre-defined views for analytics:

==== hourly_user_activity

Aggregates user activity by hour and event type.

==== sensor_stats

Provides statistics on sensor readings by hour, type, and facility.

== 🚨 Identified Issues and Improvements

=== 1. Flink SQL Implementation

*Issue*: ✅ RESOLVED - The initial Java-based Flink jobs were writing to file sinks instead of Iceberg tables.

*Solution*: The project now uses Flink SQL jobs to process data from Kafka and write directly to Iceberg tables. This approach:

1. Follows the recommended practice of using Flink Table API or SQL instead of DataStream API
2. Simplifies the code by using declarative SQL instead of imperative Java
3. Provides better integration with Iceberg through the Flink SQL connector
4. Includes proper configuration for the Iceberg catalog and S3 storage

The implementation can be found in the `flink-jobs/sql-jobs/` directory, with separate SQL files for user activity and sensor data processing.

=== 2. Java Version Mismatch

*Issue*: The project guidelines specify Java 21, but the build.gradle.kts file is configured for Java 17.

*Solution*: Update the build.gradle.kts file to use Java 21:

[source,kotlin]
----
java {
    sourceCompatibility = JavaVersion.VERSION_21
    targetCompatibility = JavaVersion.VERSION_21
}

tasks.withType<KotlinCompile> {
    kotlinOptions.jvmTarget = "21"
}
----

=== 3. Kafka Configuration and Multi-Environment Support

*Issue*: ✅ RESOLVED - The project needed to support both local Kafka and Confluent Cloud environments.

*Solution*: The project now includes:

1. A structured `config/` directory with separate configurations for local and cloud environments
2. Kafka in KRaft mode (without Zookeeper) for the local environment
3. Configuration for Confluent Cloud for the cloud environment
4. Environment switching via the `KAFKA_ENV` environment variable
5. Proper documentation in the README.adoc file

This approach allows developers to easily switch between local development and cloud deployment without code changes.

=== 4. Timestamp Handling and Event Time Processing

*Issue*: ✅ RESOLVED - The initial implementation lacked proper timestamp handling for event time processing.

*Solution*: The Flink SQL jobs now include:

1. Proper timestamp parsing with ISO-8601 format support:
   ```sql
   'json.timestamp-format.standard' = 'ISO-8601'
   ```

2. Watermark definitions for event time processing:
   ```sql
   WATERMARK FOR `timestamp` AS `timestamp` - INTERVAL '5' SECOND
   ```

3. Separate event_time and processing_time fields in the sink tables:
   ```sql
   event_time TIMESTAMP(3),
   ...
   processing_time TIMESTAMP(3)
   ```

This approach enables proper event time processing, handling of out-of-order events, and analysis of processing latency.

=== 5. Error Handling for Malformed Data

*Issue*: ✅ RESOLVED - The initial implementation lacked robust error handling for malformed data.

*Solution*: The Flink SQL jobs now include error handling for malformed JSON data:

1. JSON parsing errors are ignored to prevent job failures:
   ```sql
   'json.ignore-parse-errors' = 'true'
   ```

2. Proper JSON format configuration:
   ```sql
   'format' = 'json',
   'json.timestamp-format.standard' = 'ISO-8601'
   ```

3. Handling of nested JSON structures (e.g., location data):
   ```sql
   location ROW<lat DOUBLE, lon DOUBLE, facility STRING>
   ```

This approach ensures that the pipeline is resilient to data quality issues and can continue processing valid records even when some records are malformed.

=== 6. Makefile Improvements

*Issue*: The Makefile uses sleep in some places instead of wait/retry logic as specified in the guidelines.

*Solution*: Replace sleep commands with proper wait/retry logic as implemented in the `wait-for-service` function.

=== 7. Documentation Format

*Issue*: ✅ RESOLVED - Some documentation was in Markdown format instead of AsciiDoc as specified in the guidelines.

*Solution*: The project documentation has been converted to AsciiDoc format:

1. README.adoc now uses AsciiDoc format with proper formatting, tables, and diagrams
2. requirements.adoc contains the project requirements in AsciiDoc format
3. project_learnings.adoc (this document) uses AsciiDoc format
4. VERIFY.adoc provides verification steps in AsciiDoc format

The documentation now follows the guidelines:
* Uses one sentence per line in AsciiDoc
* Includes emoji for better readability
* Uses Mermaid diagrams inside docs
* Provides comprehensive information about the project structure and components

== 🛠️ Best Practices

=== Flink Development

1. *Use Flink SQL*: The project now follows the guideline to prefer Flink SQL over the DataStream API:
   * SQL jobs in the `flink-jobs/sql-jobs/` directory
   * Declarative approach for defining sources, transformations, and sinks
   * Better readability and maintainability
   * Easier integration with Iceberg

2. *Event Time Processing*: The SQL jobs implement proper event time processing:
   ```sql
   WATERMARK FOR `timestamp` AS `timestamp` - INTERVAL '5' SECOND
   ```

3. *Error Handling*: The SQL jobs include error handling for malformed data:
   ```sql
   'json.ignore-parse-errors' = 'true'
   ```

4. *Iceberg Integration*: Direct integration with Iceberg through the Flink SQL connector:
   ```sql
   CREATE CATALOG iceberg_catalog WITH (
     'type'='iceberg',
     'catalog-impl'='org.apache.iceberg.rest.RESTCatalog',
     'uri'='http://iceberg-rest:8181',
     'warehouse'='s3://warehouse/'
   )
   ```

=== Docker and Infrastructure

1. *Use OrbStack*: The guidelines recommend using OrbStack instead of Docker Desktop for managing containers.

2. *Docker Compose*: Don't add version attribute to docker-compose.yaml file.

3. *Kafka Configuration*: Use Apache Kafka 3.9.0 in KRaft mode without Zookeeper.

=== Build and Deployment

1. *Use Gradle with Kotlin*: The project uses Gradle with Kotlin DSL for build scripts.

2. *Use SDKMAN*: Recommended for managing Java SDKs.

3. *GitHub Actions*: Create GitHub Actions based on commands in the Makefile.

== 📊 Monitoring and Observability

The pipeline includes several monitoring points:

1. *Kafka UI*: Available at http://localhost:8080 for monitoring Kafka topics and consumers.

2. *Flink Dashboard*: Available at http://localhost:8081 for monitoring Flink jobs and performance.

3. *Trino UI*: Available at http://localhost:8082 for monitoring query execution.

4. *Minio Console*: Available at http://localhost:9001 for monitoring S3 storage.

5. *Superset*: Available at http://localhost:8088 for data visualization and dashboards.

== 🚀 Getting Started

1. Clone the repository
2. Run `make up` to start all services
3. Run `make create-tables` to create Iceberg tables
4. Run `make deploy-flink-jobs` to deploy Flink jobs
5. Access Superset at http://localhost:8088 (admin/admin) to create dashboards

For a complete demo, run `make demo` which will:
1. Build all components
2. Start all services
3. Create tables
4. Deploy Flink jobs
5. Run example queries
6. Set up Superset
